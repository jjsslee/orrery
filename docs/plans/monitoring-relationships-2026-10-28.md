## 1. 목표와 성공 기준

사용자가 이상 자원을 선택했을 때 **어떤 구성 관계로 연결된 자원을, 어떤 지표로, 어느 시간 범위에서 함께 확인해야 하는지** 설명한다. 관계의 근거·확인 시각·불확실성을 함께 제시한다.

대표 시나리오:

1. ALB의 응답 지연을 발견한다.
2. `/api/*` 조건과 대상 TG를 선택한다. 같은 TG로 향하는 다른 규칙도 확인할 수 있다.
3. TG 등록 대상과 연결된 ECS 서비스, 실행 EC2를 따라간다. 서비스의 TG 연결 설정과 실제 등록 IP/호스트는 다른 근거로 보여준다.
4. ALB/TG 응답·오류·헬스, ECS CPU·메모리, EC2 CPU·네트워크를 같은 시간 구간에서 비교한다.
5. “이전 호스트는 10:10까지 확인, 이후 조회 실패”, “10:10~10:20 사이 등록 대상 변경 관측”처럼 구성의 확인 범위를 읽는다.
6. 관련 자원은 사용자가 선택한 뒤에만 지표 조회 대상이 된다. 원인 확정이나 통신 성공으로 단정하지 않는다.

완료 기준은 관계 개수 증가가 아니다. 사용자가 **선의 의미, 근거, 신선도, 지표 범위, 다음 확인 대상**을 확인할 수 있어야 한다.

## 3. 범위와 원칙

### 포함

- 근거·관측·갱신 범위를 가진 관계 모델과 안전한 병합.
- 관련 자원 패널의 다단계 구성 탐색과 경로별 함께 보기.
- 조건·가중치·역할·실행 위치·설정 참조·정책 연결의 구분.
- 동일 시간축의 지표 비교, 지표 없는 자원의 구성 정보 표시.
- 로컬 구성 스냅샷 차이와 지표·경보 시각의 대조.
- 저장한 함께 보기의 복원, 삭제/미확인 자원 처리.
- 실패·상한·읽기 전용·계정 격리 검증과 제품 문서.

### 하지 않는 것

AWS 쓰기, 경보/추적/로그 기능 활성화, 에이전트 설치, IAM 변경, 자동 복구, 백그라운드 상시 감시·외부 알림은 추가하지 않는다. 계정 간 AssumeRole을 자동 실행하지 않는다. X-Ray/실제 요청 추적이나 IAM·SG·NACL의 종합 접근성 판정, 장애 원인 자동 확정도 범위에 넣지 않는다.

추가 CloudWatch 지표가 계정에서 활성화되지 않았다면 “미제공/관측 없음”으로 표시한다. 수집을 위해 AWS 설정을 자동 변경하지 않는다.

## 4. 사용자 화면

기존 자원 목록·관측 영역·관련 자원 패널을 유지한다. 모니터링에 전체 토폴로지 캔버스를 복제하지 않는다.

```text
[기준 자원: ECS 서비스 orders] [기간: 최근 1시간] [구성 확인 10:20 · 일부 미확인]

구성 연결                      함께 보기 (선택 4/8)              관련 자원
ALB ─ 조건 /api/* ─ TG          ALB 응답·오류                   전달 대상
                       ECS     TG 헬스·응답                    실행 호스트
                        └ EC2  ECS CPU·메모리                  데이터·설정 참조
                               EC2 CPU·네트워크                접근 정책 / 같은 태그
[조건·근거 펼치기]              [공통 시각 커서]                [과거 확인 관계 펼치기]
[이 구성의 자원 선택]           [구성 변화 관측 구간]
```

- 이름보다 자원 종류를 먼저 읽을 수 있게 현재 A안의 위계를 유지한다.
- 선/행에 “전달 대상”, “실행 호스트”, “설정 참조”, “정책에 기재” 등 의미를 표시한다. 색만으로 구분하지 않는다.
- 확인 상태는 `현재 확인`, `시간 경과`, `재확인 실패`, `구성 대상만 확인`, `이전 구성에서만 확인`으로 분리한다.
- 상세 펼침에 원본 필드/API, 마지막 성공 시각, 마지막 시도 시각, 실패 사유, 전체 조건과 대상 범위를 표시한다. 응답 원문·환경 변수 값·signed URL·시크릿은 표시하지 않는다.
- 첫 화면은 직접 이웃. “한 단계 더”로 경로를 확장한다. SG·IAM·VPC 허브의 모든 이웃을 자동 확장하지 않는다.
- “이 구성의 자원 선택”은 후보 확인 화면을 연다. 8개 초과 시 임의로 앞의 8개를 추가하지 않고 사용자가 고른다. 지표 없는 노드는 구성 맥락으로 유지하며 관측 슬롯을 차지하지 않는다.
- 기본 경보와 연결된 경보가 없는 경우를 정상 판정으로 사용하지 않는다.
- 키보드로 후보 선택/상세 펼침/닫기 가능, 포커스 보존. 축소 화면에서는 관련 자원을 접고 관측 영역을 먼저 제공한다.

## 5. 관계·관측 모델

### 서로 다른 세 축을 분리

| 축 | 값 예시 | 설명 |
|---|---|---|
| 관계 의미 | 전달, 호출 설정, 실행 호스트, 소속, 마운트 설정, 참조, 정책 기재 | 무슨 관계인지 |
| 근거 | AWS 구성 필드, 문자열 식별자 해석, 태그 일치 | 왜 연결했다고 판단했는지 |
| 관측 상태 | 현재 확인, 시간 경과, 재확인 실패, 부재 확인, 대상 미해석 | 언제 어디까지 확인됐는지 |

임의의 신뢰도 점수(예: 90%)는 도입하지 않는다. 원본 API로 관계를 확인했어도 실제 통신을 관측했다는 의미는 아니다.

제안 계약(실제 명칭은 구현 시 기존 타입 스타일에 맞춤):

- `RelationRecord`: 안정적인 ID, source/target 식별자, kind, routeGroupId, 구조화된 조건·우선순위·weight·동작 순서, evidenceIds, observation.
- `RelationEvidence`: collector, API, 원본 owner ARN/ID, fieldPath, 관계 해석 방법, 수집 runId와 성공 시각. 원본 전체 응답은 보존하지 않음.
- `CollectionPartition`: 인증 소스/계정/리전 + API family + 소유 자원 + 관계 종류. `complete/partial/failed/not-requested`, 페이지 완료 여부, attemptedAt/succeededAt/errorCode.
- `Observation`: firstSeenAt, lastConfirmedAt, lastAttemptAt, state, missingSince/absenceConfirmedAt. lastConfirmedAt은 조회 실패로 갱신하지 않음.
- `TargetResolution`: resolved / configuration-only / outside-scope / unavailable. 지표 capability와 별개.

관계 ID는 화면 label·상태·확인 시각에 의존하지 않는다. listener rule ARN·action 순서·target ARN, CloudFront distribution/behavior의 path+origin 식별자, service ARN+host ID처럼 원본의 안정적인 의미 키로 만든다. weight/조건 변경은 같은 관계의 속성 변경이 될 수 있으며, 대상 교체는 관계 제거/추가로 구분한다. 원본 ID 없는 관계는 canonical serialization과 해시를 사용하고 순서 민감/비민감 필드를 명시한다.

같은 선을 여러 수집기가 입증하면 evidence 목록을 병합한다. 한 근거만 부재가 되면 다른 현재 근거를 지우지 않는다. 상태·헬스는 관계 존재 여부와 분리한다.

태그 후보는 RelationRecord로 승격하지 않는다. 태그가 같다는 이유로 경로·의존성·영향 범위에 포함하지 않는다.

## 6. 부분 수집과 삭제 판단 — 최우선

현재 전체 합집합 방식은 제거한다. **해당 관계 집합을 완전히 열거한 성공 범위만** 부재를 판정할 수 있다.

| 새 관측 | 이전 관계 처리 | 현재 경로에 사용 |
|---|---|---|
| 같은 관계 성공 확인 | 데이터·lastConfirmedAt 갱신 | 예 |
| 소유 자원의 해당 관계 목록 전체 성공, 관계 없음 | 부재 확인으로 기록, 현재 목록에서 제거 | 아니오 |
| 일부 페이지 실패·상한 중단 | 이번에 확인한 관계만 갱신, 누락 관계는 재확인 실패 | 기본 제외, 과거 보기에서 가능 |
| 권한 거부·네트워크 오류 | 마지막 확인 기록 보존, 실패 시각/사유 기록 | 기본 제외 |
| 조회하지 않은 분할 범위 | 상태 갱신 없음, 시간 경과 여부만 계산 | 신선도 표시와 함께 명시적으로 선택 |
| 소유 자원이 목록에서 없음 | 목록의 authoritative coverage 확인 후 부재 판정 | 확인 전 삭제 단정 금지 |
| 다른 계정·소스·리전 응답 | 폐기하고 범위 오류 | 아니오 |

세부 규칙:

- 예: ALB 태그 조회 실패는 listener rule 목록의 완전성을 무효화하지 않는다. 반대로 listener rule 2페이지 실패면 1페이지 결과만으로 나머지 규칙 삭제를 판단하지 않는다.
- ECS 서비스 10개 중 1개 권한 거부는 개별 재시도로 분리하고, 이후 페이지/클러스터도 계속 수집한다. 토폴로지와 모니터링이 같은 조회 helper/실패 계약을 사용한다.
- JSON/정책 파싱 실패·응답 failures 배열·페이지 토큰 반복·취소·deadline 초과도 coverage에 반영한다. 문자열 로그에서 성공/실패를 추론하지 않는다.
- 기존 캐시에는 근거가 없으므로 “이전 형식·재확인 필요”로 읽거나 재수집한다. 과거 캐시에 현재 확인 시각을 만들어 넣지 않는다.
- 캐시 스키마는 버전을 올린다. 자동 수집 시작 전에 사용자 화면에는 기존 자료/지표를 표시할 수 있지만, 확인된 신규 관계처럼 취급하지 않는다.
- 새 결과와 차이 기록은 동일한 graph revision을 가리키게 원자적으로 저장한다. 중단 시 이전 완성 snapshot을 유지한다.

## 7. 다단계 경로 탐색

### 기본 경로와 맥락 연결

| 관계 | 자동 탐색 역할 |
|---|---|
| ALB→TG, TG→등록 대상, CloudFront→오리진, 이벤트 소스→함수 | 서비스 구성 경로 |
| ECS→EC2 실행 호스트 | 호스트 맥락. 요청이 EC2로 다시 전달된다는 화살표로 표현하지 않음 |
| 클러스터→서비스, ASG→EC2, VPC/서브넷 소속 | 묶음/포함 맥락 |
| Lambda→EFS 마운트 설정, ECR 이미지 참조 | 의존 구성. 이미지 저장소를 요청 처리 경로에 넣지 않음 |
| SG/IAM/Endpoint/AOSS 정책 | 접근 설정 맥락. 전체 허용 판정 아님 |
| 자유 설정 참조·태그 | 별도 후보. 기본 실행 경로에는 넣지 않음 |

- 그래프 원본에서 탐색한다. 화면에서 접힌 TG·집계 노드·숨김 필터 결과를 입력으로 쓰지 않는다.
- 방향·관계 종류·routeGroupId를 보존한다. 무방향 BFS로 연결된 모든 것을 서비스 경로로 합치지 않는다.
- 기본 깊이 1, 사용자 확장 최대 3단계. 응답당 최대 60노드/120관계, 후보는 20개씩 표시한다. 제한은 서버 강제이며 도달 시 “일부 표시”와 이어보기 정보를 반환한다.
- cycle을 visited 집합으로 차단하되, 같은 대상에 도달한 서로 다른 조건·경로는 삭제하지 않는다. 안정적인 정렬로 같은 revision의 결과 순서를 고정한다.
- ALB 조건은 AND/OR 구조·우선순위·기본 동작·weight=0·redirect/fixed response/auth action을 보존한다. 조건 문자열을 다시 파싱해 실행 경로를 계산하지 않는다.
- CloudFront path pattern의 우선순위, origin path, origin group의 failover 순서/기준은 분리 필드로 보존한다. 실제 요청이 어느 origin으로 갔는지는 단정하지 않는다.
- endpoint/외부 ARN/등록 IP의 상세가 없으면 configuration-only에서 탐색을 멈춘다. IP가 같다는 이유만으로 다른 VPC의 EC2와 연결하지 않는다.
- 결과에는 graphRevision, 적용 필터, 사용한 근거, truncated와 continuation을 포함한다. 서로 다른 revision의 페이지를 섞지 않는다.

## 8. 자원 식별자와 지표 capability

자원 식별자, 관측 세션 범위, 지표 조회 리전을 분리한다.

- 세션 범위: source/account/selected region. 현재 보안 경계 유지.
- 자원 식별자: ARN 우선, 없으면 account/resource region/type/native ID. 글로벌은 명시적으로 global.
- 지표 위치: namespace/dimensions/metric region으로 결정. CloudFront처럼 us-east-1에 있는 지표는 별도 표기.
- 외부 계정·미수집 리전 자원은 구성 맥락으로만 표시한다. 자동 계정 전환·임의 role assume 없음.
- 저장 그룹의 기존 4요소 키는 scope 검증 후 migration table로 복원한다. 해석 불가능한 것은 사용자가 재선택하며 이름으로 대체하지 않는다.
- 목록/그래프 병합에서 이름·태그·지표 차원 props의 출처와 관측 시각을 보존한다. 최신 필드가 “없음”인지 “미조회”인지 구분한다.
- configuration-target, SG, IAM 같은 맥락 자원은 지표 조회 요청에서 제외한다. `metricsSupported`, `alarmMappingSupported`, `relationshipOnly`를 독립적으로 계산한다.

## 9. 지표와 시간축

### 1차 경로: ALB → TG → ECS + 실행 EC2

| 단계 | 제공할 비교 정보 | 제약 |
|---|---|---|
| ALB | 요청·5xx·응답시간/p95 | 현재 프리셋 재사용. 전체 LB 지표를 `/api/*` 전용 지표로 표시 금지 |
| TG | 대상 헬스·응답·가능한 타깃 오류/요청 지표 | 지원 namespace/차원/통계 조합을 공식 문서와 더미 query fixture로 확인 후 제공 |
| ECS | CPU·메모리, 실행/희망 태스크 수의 구성 snapshot | 태스크 수를 과거 CloudWatch 시계열처럼 그리지 않음 |
| EC2 | CPU·네트워크, 모니터링 주기에 맞춘 해상도 | EC2 지표는 호스트 전체. 한 ECS 서비스 사용량으로 귀속 금지 |

TG는 자원 ID만으로 충분하지 않을 수 있다. **TG와 연결 LB의 차원 조합을 명시한 MetricContext**를 서버가 검증한다. 동일 TG의 여러 LB 맥락을 임의 선택하지 않는다. 지표 ID도 namespace/차원/통계/리전을 포함한 안정 키를 사용해 기존 `metric:stat` 충돌을 방지한다.

첫 구현부터 모든 서비스 지표를 새로 만들지 않는다. EFS·CloudFront 등 기존 프리셋은 재사용하고, AOSS는 네트워크/정책 맥락을 우선 제공한다. AOSS 신규 지표가 필요하면 실제 제공 차원과 비용을 검증한 별도 증분으로 추가한다. 기능 완성을 위해 지표를 꾸며 만들지 않는다.

시간축 원칙:

- 사용자가 선택한 범위는 동일하게 유지하되, 각 시계열의 실제 period·통계·리전·마지막 데이터 시각을 표시한다.
- 공통 커서는 같은 시각 구간을 가리킨다. 다른 주기의 점들을 단순 합치거나 결측을 0으로 보간하지 않는다.
- 0 / empty / partial / error / unsupported를 구분한다. 실패한 시계열만 재시도 가능하게 한다.
- 단위가 다른 CPU·요청 수·응답시간을 같은 y축이나 무차별 0~100 정규화로 겹치지 않는다. 소형 차트를 세로 정렬한다.
- 과거 기간을 선택해도 현재 구성만 있다면 “현재 구성 기준 후보”라고 표시한다. 역사적 토폴로지가 있다고 주장하지 않는다.
- 관계 선택·조건 펼침·후보 검색 자체는 GetMetricData를 호출하지 않는다.

## 10. API와 갱신 전략

기존 `/api/monitoring/related`를 확장하고 기존 metrics/resolve 경로를 재사용한다. 새로운 독립 그래프 엔진이나 별도 전역 상태 저장소는 만들지 않는다.

- related 요청: 기준 자원, graphRevision, 깊이, 관계 그룹, 방향, continuation. 모두 서버 허용값·상한 검증.
- related 응답: 분류별 후보, 경로/근거, 관측 상태, context-only 대상, coverage 요약, truncation.
- metrics 요청: 선택한 최대 8자원과 승인된 MetricContext. 클라이언트 임의 namespace/dimension을 그대로 AWS에 전달하지 않음.
- 관계 재확인: 해당 경로의 owner 분할 범위만 조회. 아직 targeted collector가 없는 영역은 전체 수집이 필요함을 표시하고 요청 중복을 막는다.
- 구성 갱신과 지표 갱신 스케줄은 분리한다. 1분 지표 갱신이 전체 topology 수집을 발생시키면 안 된다.
- 동시 요청은 source/account/region/partition 단위로 공유한다. 성공 snapshot revision을 비교해 늦게 도착한 응답이 최신 상태를 덮지 못하게 한다.
- 클라이언트 AbortController/세대 번호와 숨김 화면 정지는 유지한다. 공유 중인 서버 수집은 한 클라이언트 취소만으로 다른 구독자의 결과를 버리지 않는다.

조회 예산(초기 구현값, 성능 검증에서 조정 가능하나 상한 제거 금지):

| 구분 | 기준 |
|---|---|
| 지표 선택 | 기존 최대 8자원 유지 |
| 지표 쿼리/요청 | 기존 최대 100쿼리·10 SDK 호출 유지. SDK 내부 retry는 별도임을 명시 |
| 지표 캐시 | 기존 60초 유지, 동일 요청 공유 |
| 관계 TTL | 현재 10분을 초기 신선도 기준으로 사용, 실패는 TTL과 별도 |
| targeted 구성 조회 | 한 작업 최대 100 SDK 호출·60초, 기존 공용 concurrency limiter 사용 |
| 전체 구성 수집 | 모든 원본 API/페이지 시도 수 측정, 초기 1,000호출·120초 제한. 도달 시 부분 결과와 이어 재확인 제공 |
| 자동 관계 갱신 | 기본 꺼짐. 명시적 재확인과 기존 캐시 재사용 우선 |

상한은 원본 SDK 호출 시점에서 집계한다. paginator·개별 fallback·재시도 등 호출 경로가 빠지지 않아야 한다. AWS 가격을 고정 금액으로 단정하지 않고 조회 대상/쿼리 수/호출 수/캐시 사용량을 표시한다. 기존 전체 수집 제한 도입은 단독 회귀 검증을 거친다.

## 11. 구성 변화 기록

경보 시각과 구성 차이를 대조하는 기능은 신뢰 가능한 snapshot 병합 이후 구현한다.

- 새로 확인된 관계, 부재가 확인된 관계, 조건/weight/호스트 변경, 재확인 실패를 다른 종류로 기록한다.
- 변화 시각은 **마지막 성공 관측~이번 성공 관측 구간**이다. API 조회 시각을 실제 배포/변경 시각으로 표시하지 않는다.
- 첫 snapshot은 기준선이며 전체 자원을 “추가됨”으로 표시하지 않는다.
- 실패 후 복구 시 마지막 성공 범위와 비교한다. 실패 중 보이지 않은 관계를 제거/재추가 이벤트로 만들지 않는다.
- 정책 JSON의 키 순서·배열 순서(의미상 무순서만), 응답 정렬 차이를 정규화해 가짜 변화를 제거한다.
- 로컬 보관만 사용한다. 초기 상한은 scope별 최근 7일 또는 100 revisions, 전체 50MB 중 먼저 도달한 기준. 축약된 관계/evidence만 저장하고 비밀값·전체 SDK 응답은 저장하지 않는다.
- 기존 캐시 파일 권한·원자적 쓰기 방식을 재사용한다. 디스크 오류는 지표 조회를 막지 않고 기록 실패로 표시한다.
- 구성 변화가 경보보다 먼저 관측돼도 원인 확정 문구를 사용하지 않는다. CloudTrail 원인 추적은 별도 요청 없이 추가하지 않는다.

## 12. 단계별 구현과 완료 조건

| 단계 | 작업 | 주요 파일 | 완료 조건 |
|---|---|---|---|
| A. 재현과 계약 | 현행 실패 재현, 타입·식별자·coverage·stable ID 결정 | shared, collectors/types, graph/assemble, monitoring 테스트 | 아래 필수 재현 RED, 계약 예제 fixture 확정 |
| B. 관측 기반 | 수집기별 partition/evidence, ECS 목록 회복, 메타데이터 병합, 과거 합집합 제거 | collectors 공통 helper, monitoring/resources·related, cache | 실패 분할만 과거 보존, 성공 분할 부재 판정 GREEN |
| C. 근거 화면 | 현재/과거/미확인 구분, 조건 펼침, context-only 처리 | MonitoringRelated, monitoring model | 지표 호출 없이 근거·신선도 확인, 기존 선택/복원 유지 |
| D. 구성 경로 | 방향·관계 유형별 탐색, ALB/CF 조건 구조화, 제한/continuation, 경로 선택 | monitoring 관계 서비스·routes, shared, web 관련 패널 | ALB→TG→ECS + 호스트 예제, 분기/순환/미확인 처리 통과 |
| E. 경로 지표 | TG context, 동일 시간축, 8자원 선택 검증, 비용/주기 표시 | metrics catalog·monitoring/metrics, MonitoringMetrics/Selection | 실측 없는 경로별 지표를 만들지 않음, 요청 상한·계정 격리 통과 |
| F. 변화 대조 | snapshot diff·보관·변화 관측 구간 UI, 그룹 복원 보완 | cache, monitoring snapshot 모듈, web 모델·차트 | 실패 복구 가짜 변화 0, 삭제/미확인 복원 명시 |
| G. 통합·릴리즈 준비 | 대규모 fixture, 접근성, 시각 확인, 읽기 전용 검증, 문서 | 전체 표준 검사·패키지 | 필수 수용 테스트 전부 통과, 미검증 항목 명시 |

의존성: A→B→C→D→E→F→G. B가 완료되기 전에 경로 추천을 먼저 배포하지 않는다. 각 단계는 독립 검토 가능한 변경 단위로 유지한다. 구현·검증이 끝나지 않은 기능을 메뉴에 노출하지 않는다.

검토 보고서나 이 계획 작성은 구현 승인이 아니다. 이후 구현 요청 범위에 맞춰 진행하며, 커밋·푸시·릴리즈는 그때의 명시적 요청에 따른다.

## 13. 필수 테스트와 재현 행렬

### 데이터 정합성

1. ALB 태그 조회 실패 + rules 목록 성공/빈 목록: 제거된 rule 관계는 현재 경로에서 사라짐.
2. rules 2페이지 실패: 1페이지 관계는 현재 확인, 나머지는 재확인 실패. 삭제 확정 없음.
3. ECS 10개 중 한 개 거부: 나머지 개별 회복, 다음 페이지/클러스터 계속 수집.
4. 같은 관계를 두 수집기가 입증: 한 쪽 실패/삭제로 전체 관계가 사라지지 않음.
5. 조건/weight 변경: label 기반 신규/삭제 노이즈 없이 의도된 차이만 기록.
6. 0 task·host/bridge·awsvpc·복수 VPC·호스트 조회 거부를 각각 구분.
7. 외부 계정 동명 ARN, 타 리전 VPC, 다른 VPC의 같은 IP가 로컬 자원과 합쳐지지 않음.
8. 글로벌 CloudFront의 자원 범위/지표 us-east-1/경보 조회 범위를 구분.
9. 구성 대상이 실제 자원으로 해석되면 evidence/선택 맥락을 보존하며 중복 후보 제거.
10. 새 캐시/이전 형식/손상 파일/atomic write 중단을 구분하고 false freshness 없음.

### 경로와 UI

11. 순환·다중 경로·같은 TG의 여러 rules·weight 0·redirect·fixed response 분기.
12. CF default/path behavior 우선순위와 origin group을 단일 실제 요청 경로로 단정하지 않음.
13. SG/IAM/VPC 공통 허브를 통한 무관 자원 확장 없음. 태그는 경로에 포함하지 않음.
14. 깊이/노드/선/페이지 상한 및 revision 변경 시 continuation 무효 처리.
15. 숨김·접힌 TG와 무관하게 원본 관계를 탐색. 조건 전체를 키보드로 열람.
16. 관계 4개 이상 근거의 실제 펼침, 긴 조건/한글/좁은 화면 표시.
17. 8자원 초과 후보에서 자동 잘림·자동 선택 없음. context-only는 슬롯/CloudWatch 요청 제외.

### 지표·비용·경합

18. 후보 탐색/조건 펼침/경로 확장에서 GetMetricData 호출 0회.
19. 선택·기간 변경만 지표 조회. debounce/중복 공유/숨김 중단/재개·백오프 회귀 없음.
20. TG+LB namespace/dimension/stat/region 조합을 정확히 검증, 임의 차원 요청 거부.
21. 60초/300초 혼합, 결측/관측 0/부분 실패, 다른 단위 비교와 마지막 관측 시각.
22. 8자원/100쿼리/10호출 상한 및 paginator 반복/구성 조회 예산·deadline 도달.
23. 계정·프로필 전환 중 늦은 응답과 캐시가 신규 scope를 오염시키지 않음.
24. 동시에 수동 재확인/자동 지표 갱신/경로 확장 시 최신 revision과 선택을 보존.
25. SDK 변경 명령은 credential 조회/네트워크 전에 차단. 신규 read API allowlist 일치.

### 변화 기록

26. 최초 수집 변화 없음, 부분 실패/복구 가짜 삭제·추가 없음.
27. 실제 조건/대상/호스트 변경은 관측 구간으로 표시, 배포 시각으로 표기하지 않음.
28. JSON 키 순서만 바뀐 정책은 변화 없음. 의미 있는 배열 순서는 보존.
29. 보관 상한·디스크 오류·잘못된 scope 기록·시크릿/signed URL 유입 방지.
30. 저장 그룹의 삭제·미확인·미지원 대상 복원 시 조용한 대체/자동 조회 없음.

표준 검증: `npm run typecheck`, `npm test`, `npm run build`, `git diff --check`. 별도 lint script는 현재 package.json에 없으므로 통과했다고 보고하지 않는다. 버그 수정은 RED→GREEN 기록을 남긴다.

성능 fixture: 기존 감사 규모(1,353자원/1,294관계)를 참고한 익명화 fixture와 10,000노드/30,000관계 합성 그래프. 순수 경로 계산은 동일 개발 장비에서 warm 20회 p95 100ms 이하를 초기 목표로 측정한다. AWS 수집 지연과 구분해 보고하고, 충족하지 못하면 탐색 인덱스·응답 분할을 조정한다. 목표치를 측정 결과로 표현하지 않는다.

## 14. 실데이터 및 출시 확인

기본 검증은 더미 SDK 응답으로 수행한다. 실데이터 확인은 허용된 파르나스 scope에서 필요한 Describe/List/Get/BatchGet만 수행하며 AWS 설정은 변경하지 않는다. 유료 지표를 무차별 조회하지 않고 선택한 대표 경로·기간으로 제한한다. 현재 권한에서 거부되는 API는 그대로 실패 UX를 확인하고 권한 우회하지 않는다.

최종 대표 시나리오: ALB→TG→ECS(host/bridge/awsvpc)와 실행 EC2, Lambda→EFS, CloudFront→origin, AOSS network/data policy. 실계정에 없는 사례는 합성 테스트로 구분해서 보고한다. 실계정 미확인 상태로 출시하면 그 범위를 릴리즈 노트에 명시한다.

출시 전 최종 체크:

- 모든 필수 수용 테스트와 SDK read-only 테스트 통과.
- 다크/라이트 및 축소 화면에서 근거·신선도·긴 조건·공통 커서 시각 확인.
- 이전 버전의 저장 그룹·캐시 복원/전환 검증.
- 설치 패키지 버전·앱 번들·체크섬·지원 OS 실행 검증 범위 기록.
- 장애 시 이전 릴리즈 앱으로 교체 가능. 새 캐시는 버전별 분리해 이전 앱이 오해석하지 않도록 함.
- README·도식 가이드·모니터링 도움말의 설명이 실제 구현과 일치.

## 15. 구현 착수 시 결정할 항목과 추천 기본값

사용자에게 모든 세부 구현을 다시 묻지 않는다. 다음 기본값으로 시작하고, 실제 측정/데이터로 변경이 필요한 경우 이유와 영향을 기록한다.

- 첫 경로: ALB→TG→ECS + EC2 호스트.
- 초기 탐색 깊이 1, 사용자 확장 최대 3, 지표 선택 최대 8 유지.
- 과거/재확인 실패 관계는 접힌 별도 구역. 기본 추천 경로에서 제외.
- 관계 재확인 수동, 기존 지표 자동 갱신은 현재 동작 유지.
- 변화 기록 로컬 한정, 7일/100 revisions/50MB 상한.
- 인과관계 점수·자동 정상 판정·자동 지표 대상 추가는 도입하지 않음.

가장 먼저 구현할 것은 경로 UI가 아니라 **수집 범위별 coverage와 마지막 확인 시각**이다. 이 기반이 없으면 보기 좋은 경로를 만들어도 오래된 관계와 조회 실패를 구분할 수 없어 모니터링 판단을 오도한다.


## 착수 후 구현 상태 (2026-10-28)

첫 구현과 실제 검증 결과는 [구현 기록](../monitoring-relationships-implementation-2026-10-28.md)을 기준으로 한다. 관계 상태·근거·경로·TG 지표·로컬 변화 기록·상한과 패키지 검증까지 적용했다. 모든 수집기의 세부 owner 범위 분할과 targeted refresh, AWS 수집 중단 지점 재개, 실계정/OS별 실행은 아직 완료하지 않았다. 현재 재확인은 계획의 fallback인 전체 수집임을 화면에 명시한다. 이 계획의 모든 수용 항목을 검증 완료로 표시하지 않는다.
