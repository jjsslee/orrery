# 자원 중심 모니터링 재구성

작성일: 2026-10-23
상태: v0.3.0의 A/B/C 구현·로컬 통합 검증과 최종 실행파일 생성 완료. macOS ARM 실행·health·내장 자산 확인을 완료했다. v0.2.0의 메뉴 중심 화면을 대체했으며 Windows/Intel Mac 실행과 Apple 공증은 미검증이다.

로그 조회는 후속 범위다. 24시간 감지와 외부 알림은 기존 AWS 경보가 담당한다.

## 사용 흐름과 화면

사용자는 자원을 쉽게 특정하고, 그 자원과 관련된 자원을 골라 함께 CloudWatch를 확인한다.

- 모니터링 첫 화면에 이름·식별자·태그 검색과 조회 범위가 보인다. 초기 6유형의 경량 목록은 화면 진입 시 자동 조회하며, 기존 토폴로지 수집을 기다리지 않는다.
- 검색 결과의 `추가`로 모니터링 자원을 선택한다. 별도의 묶음 체크/비교 체크/지표 메뉴 이동은 없앤다. 기존 최대 4개 비교 제한은 화면에 명시한다.
- 선택하면 같은 화면의 자원별 CloudWatch 지표와 관련 경보를 조회한다. 짧은 debounce로 연속 선택을 합치며 검색 입력이나 후보 탐색 자체는 지표를 재조회하지 않는다. 지표 조회의 비용 가능성과 실제 데이터 시각은 화면에 남긴다.
- 기준 자원을 누르면 `선으로 연결된 자원`과 `같은 태그의 자원`을 쉽게 볼 수 있다. 각 후보에 관계 종류·방향 또는 일치한 태그 키·값을 표시하고, 사용자가 고른 후보만 추가한다. 후보 선택은 원인 판정이나 자동 포함을 뜻하지 않는다.
- 토폴로지 연결은 기존 그래프 캐시를 재사용하고, 필요할 때 백그라운드로 수집한다. 같은 태그 후보와 선택한 자원의 CloudWatch 조회는 연결 수집 완료에 의존하지 않는다. 일부 수집 실패를 `관계 없음`으로 표시하지 않는다.
- 현재 선택을 이름 붙여 저장·복원한다. 저장은 source/account/region별 로컬 설정이며 기존 v1 관심 묶음도 보존한다. 4개를 넘는 기존 묶음은 조용히 자르지 않고 사용자가 대상을 고르게 한다.
- 전체 경보 대시보드를 첫 화면으로 사용하지 않는다. 선택한 자원에 매핑된 경보와 원문 조건/이력을 그 자원 아래에서 확인한다. 매핑하지 못한 경보는 별도 안내로 남기며 정상으로 단정하지 않는다.
- 기간과 자동 갱신은 선택 자원 전체에 공통 적용한다. 숨김/메뉴 이탈/계정 변경 중단, 오류·권한·부분·결측 처리 및 읽기 전용 보장은 유지한다.

화면 구성: 자원 검색·선택 목록 / 선택 자원의 지표·경보 / 기준 자원의 관련 자원 후보. 좁은 화면에서는 검색·선택·관련 후보·관측 결과를 읽는 순서로 쌓는다.

## 구현과 검증

### A. 관련 자원 데이터 경로

상태: 구현·mock 검증 완료. 모니터링 첫 진입과 선택 지표 조회는 전체 그래프 수집을 기다리지 않는다.

- `/api/monitoring/related`에서 양방향 one-hop 연결과 정확한 태그 key/value 일치를 반환한다. 자기 자신과 중복 후보를 제외하고 방향·관계 종류·태그 근거를 보존한다. 기존 edge에 직접 확인/추정 출처가 없어 근거의 해당 구분은 `unknown`으로 명시한다.
- 기존 그래프 캐시를 재사용하고 연결이 필요할 때 백그라운드 수집한다. source/account/region별 cache/inflight를 분리하고, 부분 실패·오류 때 이전 후보와 마지막 성공 시각을 유지한다. 명시적 재조회는 최신·부분 캐시에도 적용하며 진행 중 수집은 공유한다.
- 그래프 출신 자원은 실제 scope 확인 후 서버 인덱스에 등록한다. CloudFront 등 기존 카탈로그 지원 자원은 같은 선택 지표 API로 조회하며 임의 namespace/dimension/명령은 받지 않는다. 미지원 지표와 경보 매핑 한계, 선택 리전 밖 경보 조회 한계를 표시한다.
- `/api/monitoring/resources/resolve`는 저장된 자원 키의 계정·리전을 검증하고 최대 100개를 확인한다. 4개를 넘는 구성을 잘라내지 않으며 실제 비교의 최대 4개 제한과 분리한다. graph-only 키의 확인도 경량 자원·선택 지표 조회를 막지 않는다.
- 경보 이력은 성공·실패 응답 모두 필수 `scope`를 반환하여 동일 프로필의 계정 변경을 구분한다.

검증 결과:

- 부분 그래프가 이전 연결을 지우는 실패(기존 연결 3개가 0개로 줄어듦)를 RED로 확인한 뒤 이전 후보 병합으로 GREEN을 확인했다.
- 최신 complete/partial 캐시에서 명시적 재조회가 수집을 시작하지 않는 실패(`complete`와 기대한 `loading` 불일치)를 RED로 확인한 뒤 강제 재조회·진행 요청 공유로 GREEN을 확인했다.
- 경보 이력 응답의 실제 계정 scope가 없는 실패(`undefined`)를 RED로 확인한 뒤 동일 프로필 계정 전환의 성공·권한 오류 응답 모두 scope를 보존하도록 수정해 GREEN을 확인했다.
- route/mock 통합으로 양방향 연결·정확한 태그·중복 제외, 계정/source 격리, 복원 키 거부, CloudFront 복원 후 지표 POST와 `us-east-1` dimensions, 미지원 지표의 호출 차단, 연결 수집 중 경량 목록·지표 독립 응답, 6개 저장 키의 무삭제 복원을 확인했다.
- `npm run test -w server`: 최종 73개 통과. `npm run typecheck -w server`: 통과. 이 절의 검증은 mock이며 실제 AWS 조회·실계정 일치 검증과 구분한다.

### B. 자원 중심 상태와 화면

상태: 구현 완료. 개요·경보·지표·자원 찾기의 네 메뉴와 별도 묶음/비교 체크를 없애고 검색·선택 / 자원별 CloudWatch / 관련 후보로 재구성했다. 기존 topology 스타일과 상단바의 반응형 규칙은 유지했다.

- 첫 화면에 이름·태그 검색, 열린 태그 키·값 필터, 유형 필터와 조회 범위를 제공한다. 기존 그래프 출신 유형도 필터에 나타난다. 선택은 검색과 분리하고 최대 4개로 표시한다.
- 기준 자원에 따라 양방향 연결의 종류·방향과 정확히 일치하는 태그 근거를 표시한다. 현재 그래프 모델이 직접 확인/추정 출처를 구별하지 않으므로 `직접 확인·추정 구분 미제공`을 명시한다. 연결 수집의 대기·오류·부분 결과를 관계 없음으로 표시하지 않는다.
- 자원을 추가하면 같은 화면에 지표와 관련 경보가 나타나며, 관련 경보를 긴 지표 목록보다 먼저 배치했다. 미지원 지표는 유료 요청에서 제외하고, 미지원 경보 매핑·선택 리전 한계도 표시한다.
- 현재 선택의 저장·복원과 기존 v1 구성 보존을 한 흐름으로 제공한다. 4개가 넘는 구성은 후보 중 직접 추가하게 하고 미확인 자원을 별도로 표시한다.
- 검증: 기존 메뉴 계약 테스트 두 개는 변경된 제품 요구에 따라 새 작업 화면 계약으로 대체했다. 새 UI 계약 3개가 이전 화면에서 실패(검색/명시적 추가/동일 화면 지표/관련 근거 부재)하는 RED를 확인한 뒤 GREEN으로 전환했다. 후속 UI 테스트는 태그 키·값 기본 노출, 경보가 차트보다 앞서는 순서, 경보 매핑/리전 한계, 연결 수집 중 표시를 확인한다. 테스트 assertion·읽기 전용 가드는 약화하지 않았다.

구현 항목:

- Monitoring 주 화면을 새 흐름으로 교체하고 더는 쓰지 않는 메뉴 화면·스타일만 제거한다.
- 선택·기준 자원·관련 후보·기간·저장 구성 상태를 account 및 요청 세대로 격리한다.
- 초기 목록과 후보 탐색에서 유료 지표 요청이 없고, 실제 선택/기간 변경 때만 debounce 후 선택 범위의 지표를 조회한다. 최대 4개와 기존 API 제한을 유지한다.
- 검증: 후보를 눌러 추가/제거, 검색 중 선택 보존, 늦은 응답·프로필 전환·연속 선택, 저장 복원, 권한 오류, 목록/관계 수집 중 지표 표시.

### C 검증 기록 — 2026-10-23

- UI 계약: 새 작업 화면의 SSR 렌더링 테스트 4개 통과. 이름·태그 검색/명시적 추가/동일 화면의 자원별 경보·지표/관련 근거/매핑·리전 한계를 검증한다. `npm test` 서버 73개 + 웹 53개, 총 126개 통과. `npm run typecheck` shared/server/web 전체 통과. 목록 새로고침 수정을 포함한 최종 `npm run build` 통과(v0.3.0, 내장 웹 자산 `index-CxuLMD0P.js`). `git diff --check` 통과.
- 목록 새로고침 회귀: 명시적 **자원 목록 새로고침** 클릭은 6유형 모두 `refresh=1`로 요청하며 유료 지표 호출은 0회임을 실제 브라우저에서 확인했다. 초기 자동 목록 조회의 기본 캐시는 유지하며 서버 route 회귀 테스트로 확인했다. 이 수정 후 `npm test` 126개와 전체 typecheck를 다시 통과했다. 최종 재빌드와 실행파일 재생성도 통과했다.
- fixture 브라우저: 이름 검색 → 추가 → 같은 태그·선 연결 후보 추가, 최대 4개 제한, 선택 구성 저장·복원, 기간 변경, 태그 키·값 필터, 경보 상세·이력, 값 표를 확인했다. 검색·태그 필터는 추가 지표 호출을 만들지 않았다. 연결 구성이 `loading`인 동안에도 지표와 태그 후보가 먼저 나타났다. 숨김 상태의 기간 변경은 지표를 조회하지 않고 화면이 보이면 재개했으며 키보드 포커스 외곽선도 확인했다. 직접 선택한 시작·종료 입력 변경 후 300ms debounce 뒤 지표 재조회를 확인했다. 실제 API와 같은 scope 필드를 포함한 경보 상세·이력 fixture가 표시됐으며 오류는 없었다. 최종 clean reload의 browser console error와 page error는 모두 0개였다.
- 화면: 1440px 다크와 640/360px 라이트에서 본문 가로 넘침이 없고 관련 후보 추가가 동작했다. 360px 상단 연결 컨트롤의 축소 문제를 모니터링 헤더 자식의 `flex-shrink: 0`/`white-space: nowrap`으로 수정하고 재확인했다. `다시 연결`은 폭 56.5px/높이 21.4px을 유지했다. 상단 컨트롤 영역은 clientWidth 340px/scrollWidth 458px이며 가로 스크롤 118.5px 이동을 확인했다. viewport와 document 폭은 모두 360px으로 본문 전체 넘침은 없었다.
- 실계정 읽기 검증: `gs-parnas-dev` / `211125409037` / `ap-northeast-2` identity가 일치했다. Lambda 목록 40개를 완료했고 일부 태그 권한의 미조회 상태를 구분했다. `parnas-stt-console` 관련 조회 첫 응답은 구성 `loading`과 같은 태그 후보 2개를 즉시 반환했다. 백그라운드 수집 약 35초 후 구성 `complete`, 선 연결 후보 12개·같은 태그 후보 40개를 확인했다.
- 제한된 유료 조회: `ninetree-cx-batch-dev`, `parnas-stt-console` 두 Lambda의 최근 3시간/60초 집계에서 `Invocations:Sum`, `Errors:Sum`, `Duration:Average`를 조회했다. 앱 POST 1회, `GetMetricData` SDK command 1회/6개 쿼리였고 결과는 모두 `empty`였다. 이 실행으로 실제 값이 있는 시계열의 렌더링을 검증했다고 주장하지 않으며 값·부분·오류·결측·단일 점은 fixture로 검증했다.
- 최종 패키징: `node scripts/package.mjs`의 모든 타깃 생성에 성공했다. macOS/Windows zip의 `unzip -tq` 검사, Windows `PE32+ x86-64` 형식 검사, macOS `codesign --verify --deep --strict` 검사를 통과했다. 서명 확인은 Apple Developer ID 공증을 뜻하지 않는다.
- 실행 확인: macOS ARM 실행파일을 4834 포트에서 실행해 health의 `{ok:true,readOnly:true,build:"0.3.0+20261023T074320Z"}`를 확인했다. 내장 JS `index-CxuLMD0P.js`에 새 자원 중심 화면·태그 조건 추가·선 연결·자동 조회 안내가 포함됐음을 확인했다. Windows/Intel Mac 실제 실행, Apple 공증, AWS 콘솔 UI 대조는 미검증이다.
