# 관계 기반 모니터링 구현 기록 — 2026-10-28

> 과거 설계·검증 기록입니다. 현재 사용자 안내는 [문서 목록](README.md)에서 확인하세요. 당시 승인·예상 비용은 새 실행 권한이 아니며, 실환경 식별자는 공개 문서용 예시로 대체했습니다.

기준: v0.8.1 이후 작업 트리. AWS 쓰기 권한/명령을 추가하지 않았으며 이번 구현 검증은 더미 SDK 응답과 합성 데이터로 수행했다. 실계정 API 호출은 하지 않았다. 이 문서는 커밋·배포 완료 기록이 아니다.

## 적용 내용

- 관계에 조회 범위(coverage), 근거(evidence), 현재/미확인/부재/이전 형식 상태, 최초·마지막 확인·최근 시도 시각을 붙였다.
- 기존 부분 수집 결과의 과거 관계 합집합을 제거했다. 성공한 범위에서 사라진 관계만 부재로 판정하며 실패한 범위는 과거 목록에 둔다. 동일 관계의 여러 출처 중 실패한 근거도 잃지 않는다.
- 원본 관계는 수집됐지만 연결 대상 노드가 미수집된 경우, 이를 관계 삭제로 오인하지 않는다. 전체 재확인 실패도 이전 관계를 현재 후보에서 분리한다.
- ALB listener rules/TG health, CloudFront distribution, ECS service/runtime에 별도 근거를 연결했다. 원본 rule·behavior·service target 식별자를 사용해 조건 변경이 단순 신규/삭제로 갈라지는 것을 줄였다.
- paginator의 후속 페이지 실패 시 `attempt`로 읽은 앞 페이지 결과를 남기고 coverage는 부분 실패로 표시한다.
- ECS 서비스 batch 실패/일부 누락 시 개별 재조회하며 다음 batch/클러스터 수집을 계속한다. 토폴로지와 모니터링이 같은 helper를 사용한다.
- 그래프/경량 자원 목록 병합에서 기존 지표 차원 props를 보존한다. 외부·미수집 대상에는 기존 configuration-target을 유지한다.

## 화면과 경로

- 직접 관계는 방향·구성 근거/식별자 해석·마지막 확인/시도를 표시한다. 4번째 이후 근거도 실제로 펼쳐 볼 수 있다.
- 구성 경로는 상류와 하류 방향을 따로 유지하는 최대 3단계 탐색이다. TG를 거쳐 무관한 형제 LB로 확장하지 않는다. weight=0 전달은 실행 후보에서 제외하고 헬스 inactive만으로 구성 경로를 없애지는 않는다.
- 소속·정책 맥락은 직접 이웃만 표시한다. 실행 호스트와 구성 대상/IP는 탐색 종점이며 SG/IAM/VPC 허브를 통한 무관 자원 확장을 막는다.
- 60자원/120관계 페이지, 10,000관계 탐색 상한과 revision 검증을 적용한다. 다음 페이지는 revision을 요구하며 기준 구성이 바뀌면 409로 다시 확인하도록 한다.
- 구성 전용 자원은 8개 비교 슬롯에서 제외한다. 과거 관계에는 추가 버튼을 제공하지 않는다. 후보/조건/ALB 선택은 지표 조회나 선택 목록 변경을 일으키지 않는다.
- 과거 기간을 보더라도 현재 구성 기준 후보임을 표시한다. ALB/TG와 EC2는 자원 전체 지표임을 카드에 명시했다.

## Target Group 지표

AWS에서 수집한 TG의 연결 ALB 목록만 서버가 맥락으로 제공한다. 사용자가 직접 선택해야 지표 비교에 추가되며 임의 ARN/차원은 거부한다. NLB/GWLB TG 신규 프리셋은 제공하지 않는다.

| Namespace | Dimensions | Metric | Stat |
|---|---|---|---|
| AWS/ApplicationELB | LoadBalancer + TargetGroup | HealthyHostCount | Minimum |
| AWS/ApplicationELB | LoadBalancer + TargetGroup | UnHealthyHostCount | Maximum |
| AWS/ApplicationELB | LoadBalancer + TargetGroup | HTTPCode_Target_5XX_Count | Sum |
| AWS/ApplicationELB | LoadBalancer + TargetGroup | TargetResponseTime | p95 |

[공식 ALB CloudWatch 지표 문서](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-cloudwatch-metrics.html)를 확인하고 정확한 namespace/dimensions/stat fixture를 검사했다. 결측을 0으로 바꾸지 않는다. TG 시리즈 식별자는 namespace/차원/통계/리전을 포함하고 그대로 재조회 필터에 사용할 수 있다. 기존 지표 ID는 호환을 유지한다.

## 이력·조회 상한

- 첫 snapshot은 기준선이다. 추가·부재·조건 변경을 기록하고 실패/복구만으로 삭제/추가 이력을 만들지 않는다. JSON 객체 키 순서를 정규화하되 의미 있는 배열 순서는 보존한다.
- 변경 시간은 마지막 성공 확인~이번 확인 구간이다. 차트 위 음영과 상세 목록은 같은 관측 구간을 보여주며 실제 배포 시각·장애 인과관계를 주장하지 않는다.
- scope별 7일, 변화가 있는 최근 100회 관측, 관계/변화 각각 5,000개를 보관한다. 이전 노드의 props/refs/tags는 이력용 노드에 복사하지 않는다.
- 캐시 전체 이력 payload 50MiB를 넘으면 오래된 이력부터 제거하고 현재 토폴로지는 남긴다. 기존 private directory/file 권한과 원자적 쓰기를 재사용한다. 저장 실패는 응답에 표시하고 메모리 결과는 유지한다.
- graph-v9 캐시로 기존 앱 데이터와 분리했다. 동일 scope의 전체 수집을 공유한다.
- 구성 수집기는 작업당 1,000 SDK 명령/120초, 지표는 기존 8자원/100쿼리/10명령/60초 캐시를 유지한다. SDK 내부 retry는 명령 수와 별개다. 경보는 독립 조회/캐시이므로 구성 명령 수에 포함하지 않는다.
- 저장 그룹의 기존 키 형식을 유지한다. 해석/확인하지 못한 자원을 예전 목록으로 조용히 대체하지 않는다. TG는 ALB 맥락을 다시 선택해야 하므로 복원 시 자동 추가하지 않고 안내한다.

## 확인한 회귀 사례

실계정 없이 다음을 실행했다.

- 성공한 rules 범위의 관계 제거 + 무관한 다른 수집 실패, 실패 범위의 마지막 확인 시각 보존.
- 여러 근거 중 하나 실패, 실패 후 복구, 실제 제거 후 재등장, 첫 관측 기준선, 정책 JSON 키 순서 변화.
- 늦거나 scope가 다른 snapshot 거부, 이미 보관된 revision 재처리의 멱등성, 미수집 endpoint와 실제 관계 삭제 구분.
- ECS 실패 batch의 정상 서비스 회복과 다음 batch 계속 처리.
- 순환/방향/공통 허브/weight=0/헬스 inactive, 페이지 상한과 revision 불일치.
- TG 정확한 지표 차원, 임의 맥락 거부, 반환된 지표 ID를 통한 정확한 재조회.
- 구성 SDK 호출 상한/deadline, 저장 실패의 메모리 유지, 50MiB 이력 제거 후 현재 그래프 보존.
- 기존 readonly middleware, 계정 격리, 최대 선택/쿼리/호출, 캐시/갱신/숨김 화면 관련 테스트.

브라우저에서 실제 컴포넌트를 더미 데이터로 렌더링해 다크·라이트 및 800×900 화면을 확인했다. 긴 조건/4번째 이후 근거/과거 관계 펼침, TG ALB 선택 전후 추가 버튼, 기존 차트 유지, 선택만으로 지표 호출 0회를 확인했다. 800px 화면의 document scrollWidth는 800px였다. 임시 fixture/서버/탭은 정리했다.

합성 성능: 10,000노드/29,997관계, warm 20회 p95 최종 측정 25.4ms. 테스트 목표 100ms 이하이며 실제 AWS 수집 지연과 무관하다.

## 남은 범위와 출시 시 확인

- 모든 수집기의 owner/API별 세분화는 완료하지 않았다. 위에서 명시한 범위 외에는 collector 단위로 보수적으로 판정하므로 불확실한 삭제는 과거·미확인으로 남을 수 있다.
- 특정 owner만 읽는 targeted refresh와 중단한 AWS 페이지에서 재개하는 기능은 없다. 전체 구성 재확인과 그래프 결과 페이지 이동을 구분해 표시한다.
- 관계 그룹은 실행/맥락 2종이며, 경로 전체 자동 선택·임의 방향 필터는 제공하지 않는다.
- 관계 원본의 조건은 보존하지만 ALB redirect/fixed response를 별도 시각 노드로 만들거나 실제 요청을 시뮬레이션하지 않는다.
- 보관 범위 밖의 시점에 역사적 토폴로지를 복원하거나 CloudTrail로 원인을 추적하지 않는다.
- 실계정 권한·실제 CloudWatch 값·설치 앱 실행/OS별 동작·Apple 공증은 이번 변경에서 검증하지 않았다.
- 커밋·푸시·릴리즈는 수행하지 않았다. 계획의 모든 세부 항목을 완료했다고 간주하지 않는다.

## 실행 화면의 부분 실패 안내 수정

사용자 화면에서 전체 수집의 ECR/ElastiCache/CodeBuild/DynamoDB 권한 오류가 관련 자원 전체 요청 실패로 표시되고 긴 원문이 중복 노출되는 문제를 수정했다. graph.observation.error는 수집 진단으로 유지하고 relatedError에는 요청 자체의 실패만 넣는다. 부분 성공·전체 실패·시간 경과 안내를 구분하며 원문은 기본 닫힌 ‘수집 오류 상세’와 최대 240px 내부 스크롤에 둔다. coverage 상세에도 스크롤 상한을 적용했다. 확인된 후보는 그대로 제공한다. AWS 권한 변경이나 실계정 재조회는 하지 않았다.

긴 AccessDenied 문자열 100개를 사용한 재현 테스트의 실패를 확인한 뒤 수정했으며, 원문이 접힌 상세에 한 번만 존재하고 부분 결과를 요청 실패로 승격하지 않는 테스트를 추가했다.

수정 후 검증: 타입 검사, 232개 테스트(server 144/web 85/desktop 3), 웹 빌드 통과. 3종 실행 패키지 재생성 및 ZIP 무결성/두 Mac 서명 확인 완료. 새 로컬 빌드 `0.8.1+20261028T055508Z`, 공통 app.asar SHA-256 `01ab922baef4d16c3b860cc996a597a6ffab777103b3d2faf4a348efb92d89e6`. 이번 안내 수정은 렌더링·상태 회귀 테스트로 검증했으며 실계정/설치 앱 실행은 다시 수행하지 않았다.

## v0.9.0 릴리즈 준비

사용자의 커밋·푸시·릴리즈 요청에 따라 root package/lock 버전을 0.9.0으로 올렸다. 타입 검사와 232개 테스트를 다시 통과했고 빌드 `0.9.0+20261028T060524Z`로 3종 패키지를 생성했다. 두 macOS 앱 서명과 플랫폼별 app.asar 동일성을 확인했다(SHA-256 `b2bf3148901d5dfebec1446dc380536f0dd709a9347d2ea0349b94214a1f63dd`). 위 0.8.1 빌드 기록은 이전 로컬 검증 시점의 기록이다. 실계정·OS별 실행 미검증 및 잔여 범위는 동일하다.
